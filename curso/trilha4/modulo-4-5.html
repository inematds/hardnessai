1

💰 Não precisa do modelo caro

Pocock desmonta o hype: aquele bug profundo que o modelo novo "achou" você também acha com um harness certo e um modelo mais barato — se olhar nos lugares certos com o prompt certo.

💰 Harness > modelo caro

Insights profundos vêm de um bom sistema de checagem, não de pagar mais por token.

  • •Modelo barato + bom harness acha o mesmo.
  • •O segredo é onde e como você procura.
  • •Não há mágica exclusiva do modelo caro.
2

🛡️ Cron de security review

Exemplo concreto: um cron diário que roda uma security review, checando uma parte diferente do repo a cada dia. Resultados decentes, modelo simples.

Cron de security review
# diário, rotativo por parte do repo
schedule: cron "0 3 * * *"
→ agente revisa um módulo diferente
→ abre issue se achar algo
3

📡 Telemetria → issue → fix

Com observabilidade (Sentry, etc.), um bug de produção vira issue automaticamente → o agente explora → propõe fix → review. O sistema reage sozinho.

4

🚲 A causa raiz do bug

A lição de ouro: "se alguém fica roubando sua bike, compre um cadeado". Não corrija só o bug — pergunte por que ele existiu tanto tempo e ataque a causa raiz.

⚠️ Não pare no sintoma

Corrigir o bug e seguir em frente é miopia. O 10x builder pergunta como aquilo passou despercebido e conserta o sistema.

5

🔄 Loops de auto-melhoria

Engenheiros sempre fizeram isso: testes, reviews humanos, refatoração. Construa loops que checam seu próprio código — sistemas que melhoram com o tempo.

✓ Sistema que se cuida

  • ✓Testes que pegam regressão
  • ✓Cron de review
  • ✓Corrige a causa raiz

✗ Sistema reativo

  • ✗Só conserta quando quebra
  • ✗Depende do modelo caro
  • ✗Repete o mesmo bug
6

🔬 Revisar o sistema

O pulo do gato: você não revisa só o código — revisa o sistema que produz o código. Melhorar o harness ao longo do tempo é o que separa os 10x builders.

Auto-recuperação (opcional): qual a atitude do "10x builder" diante de um bug antigo?
