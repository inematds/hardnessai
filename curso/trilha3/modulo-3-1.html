1

🧬 O que é uma skill

Uma skill é uma unidade reutilizável de comportamento — um pedaço de instrução que você empacota uma vez e o agente passa a executar do mesmo jeito, toda vez. Em vez de re-explicar um procedimento a cada conversa, você o congela num arquivo e o invoca por nome.

📦 A skill é um comportamento empacotado

No vocabulário do Matt, a skill é onde mora o seu conhecimento humano de processo. Ela não é mais inteligência dentro do modelo — é estrutura no harness, que você controla.

  • •Reutilizável — escreve uma vez, usa em todo projeto e todo agente.
  • •Nomeável — tem um nome que você (ou o modelo) chama.
  • •Portável — roda no Claude Code, no Codex, em qualquer harness.
  • •Versionável — você melhora, distribui pro time, recebe de volta.

🧠 DRY humano

“Fiz esse plano 100 vezes → viro skill, distribuo pro time, todo mundo planeja igual e contribui de volta, levantando o piso.” A skill é o seu don't repeat yourself aplicado ao raciocínio — não só ao código.

2

📝 Frontmatter e corpo

Anatomicamente, toda skill tem duas partes: o frontmatter (a descrição, no topo) e o corpo (as instruções de verdade). A descrição é a vitrine — é o que o modelo lê pra decidir se aquela skill serve. O corpo só entra em jogo quando a skill é de fato acionada.

💡 Por que a descrição é tão delicada

A description sempre vaza para a janela de contexto — ela fica lá mesmo quando a skill não roda. Por isso ela precisa ser curta e precisa: boa o bastante pra o modelo saber quando puxar, enxuta o bastante pra não custar contexto à toa. (Vamos fundo nesse custo no módulo 3.2.)

📄 Frontmatter (a vitrine)

  • •Nome e descrição da skill.
  • •Quando o modelo deve considerá-la.
  • •Flags, como disable model invocation.

📜 Corpo (as instruções)

  • •O passo a passo que o modelo segue.
  • •Padrões, exemplos, restrições.
  • •Só carregado quando a skill roda.
3

🎛️ Procedures (você invoca)

O primeiro tipo de skill é a procedure: você a dispara. É um botão que você aperta para fazer o modelo se comportar de um jeito específico — “rode a grill-me”, “gere o PRD”, “quebre em issues”. Quem decide o quando é o humano.

1

Você dá o gatilho

A procedure não dispara sozinha. Você a chama pelo nome no momento em que quer aquele comportamento.

2

O modelo assume o modo

Ao ser invocada, ela faz o modelo se comportar de um jeito — entrevistador adversarial, redator de PRD, triador de tarefas.

3

Você fica no volante

O pensamento sobre quando agir não é delegado. Procedures encadeiam: grill-me → two-PRD → to-issues, sob seu comando.

🔗 Procedures encadeiam

É assim que o Matt monta o pipeline de pensamento dele: cada procedure é um elo que ele dispara na ordem que faz sentido — não um agente solto decidindo por conta própria.

4

🤖 Abilities (o modelo invoca)

O segundo tipo é a ability: o modelo a puxa sozinho, quando percebe que ela se aplica. O exemplo do Matt é um “coding standards”: na hora de escrever React, o modelo lê a description, decide que é relevante e aplica — “shouldn't use useEffect, should use something different”.

⚛️ Exemplo: coding standards ao escrever React

O modelo vai escrever um componente React. Sem você pedir nada, ele reconhece a situação pela description da skill e puxa o padrão:

  • •“shouldn't use useEffect” → usa outra abordagem.
  • •O gatilho é o contexto da tarefa, não o seu comando.
  • •É o modelo decidindo o quando — você só deixou a skill disponível.

⚠️ O preço de deixar o modelo decidir

Abilities são convenientes, mas você terceiriza o julgamento de quando agir. E como a description precisa estar sempre visível pro modelo poder puxá-la, toda ability paga pedágio no contexto — 100 skills, 100 descrições.

5

🚪 As duas portas

Toda skill entra por uma de duas portas. Na procedure, quem abre é você. Na ability, quem abre é o modelo. Mesma anatomia, decisor diferente — e é isso que define quem está dirigindo.

🎛️ Procedure — humano no volante

  • •Você decide o quando.
  • •O pensamento fica com você.
  • •É a preferida do Matt.

🤖 Ability — modelo no volante

  • •O modelo decide o quando.
  • •Conveniência ao custo de julgamento.
  • •A abordagem que o Superpowers prefere.

🧭 A preferência do Matt

“I know my skills, I don't want to delegate my thinking.” Matt prefere procedures: esconde a maioria das descrições do modelo e mantém o conhecimento no humano. O Superpowers (Obra) prefere o oposto — modelo no controle. A diferença é de filosofia, não de capacidade.

6

🎯 Qual usar quando

Fechando o módulo: o critério é quem deve decidir o quando. Se o julgamento é seu e você quer ficar no volante, faça uma procedure. Se a regra se aplica sempre que um certo contexto aparece e você confia no modelo pra reconhecê-lo, uma ability poupa cliques.

💡 A pergunta de bolso

Antes de criar a skill, pergunte: eu quero apertar o botão, ou quero que isso aconteça automático? Se a resposta envolve pensamento — escopo, plano, decisão de produto — prefira procedure e mantenha o controle.

Pensamento?

Se exige julgamento → procedure.

Regra fixa?

Vale sempre num contexto → ability.

Custo de contexto?

Muitas abilities incham → esconda.

Default do Matt

Na dúvida, procedure.

📌 Lembrete

Você pode esconder a description de uma skill com disable model invocation: true — ela vira uma procedure pura, sem vazar pro contexto e sem o modelo poder puxá-la. É o caminho do Matt pra manter o humano no comando.
